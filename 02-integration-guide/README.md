# Этап 2. Интеграционный гайд (Quick Start) и Postman-коллекция

## 📌 Назначение
Когда смежные команды или внешние системы подключаются к сервису справок и выписок, одной спецификации Swagger недостаточно — нужен понятный сценарий первого запуска и готовый инструмент для проверки.

Этот раздел решает две задачи:
* Помогает командам интеграции самостоятельно выполнить первый запрос по `cURL` с соблюдением правил идемпотентности и лимитов.
* Дает инженерам L2-поддержки готовую Postman-коллекцию для быстрого воспроизведения обращений и проверки контракта на тестовом контуре (`Stage`).

---

## 🚀 Quick Start Guide: Сервис «Справки и выписки»

Перед началом интеграции убедитесь, что для вашей системы выдан `Client-ID` и настроена авторизация на тестовом контуре (`Stage`).

### 1. Базовые параметры
* **Base URL (Stage):** `https://api-stage.bank.internal/v1`
* **Формат данных:** `application/json; charset=utf-8`
* **Авторизация:** заголовок `Authorization: Bearer <JWT_TOKEN>`

### 2. Обязательные заголовки
| Заголовок | Тип | Описание |
| :--- | :--- | :--- |
| `Authorization` | `String` | Bearer-токен сервисной учетной записи |
| `X-Idempotency-Key` | `UUIDv4` | Уникальный ключ запроса для защиты от дублирования заявок |
| `Content-Type` | `String` | Всегда `application/json` |

### 3. Пример запроса (cURL) — заказ выписки по счету
```bash
curl --location 'https://api-stage.bank.internal/v1/documents/process' \
--header 'Content-Type: application/json' \
--header 'Authorization: Bearer eyJhbGciOiJIUzI1NiIsIn...' \
--header 'X-Idempotency-Key: c9b2c8a1-6e3e-4b77-8f55-123456789abc' \
--data '{
    "externalId": "CRM-STMT-10928",
    "docType": "ACCOUNT_STATEMENT",
    "payloadBase64": "JVBERi0xLjQKJcOkw7zDtsOf..."
}'
```

## 🛡️ Надежность и ограничения

### 1. Механизм идемпотентности (`X-Idempotency-Key`)
API защищен от дублирования заявок на выпуск справок при сетевых сбоях и таймаутах:
* **Время жизни ключа (TTL):** сервер кэширует ключ и результат обработки на **24 часа**.
* **Повторный вызов:** при повторной отправке запроса с тем же `X-Idempotency-Key` дубликат не создается — возвращается первоначальный ответ со статусом `HTTP 201 Created` и заголовком `X-Cache-Lookup: HIT`.
* **Race condition (запрос еще в работе):** если первый запрос с этим ключом еще обрабатывается, сервер вернет `HTTP 409 Conflict`. Интегратору нужно повторить запрос позже.

### 2. Ограничение частоты вызовов (Rate Limiting)
* **Лимит:** не более **60 запросов в минуту** на одну сервисную учетную запись.
* **Превышение лимита:** сервер возвращает `HTTP 429 Too Many Requests` и заголовок `Retry-After` (через сколько секунд можно повторить вызов).
* **Рекомендация при `429` и `504`:** использовать стратегию *Exponential Backoff* (повтор через `2`, `4`, `8` секунд со случайной задержкой / jitter).

## 🧪 Архитектура коллекции Postman

👉 [Скачать файл коллекции (JSON)](./document-service.postman_collection.json)

### 1. Переменные окружения (Environments)
Коллекция параметризована для быстрого переключения между контурами:
* `{{baseUrl}}` — хост окружения (`stage` / `prod`).
* `{{jwtToken}}` — токен авторизации.
* `{{lastCreatedDocId}}` — переменная, куда автоматически сохраняется `documentId` созданной заявки.

### 2. Pre-request Script (автогенерация ключа идемпотентности)
Скрипт автоматически подставляет новый `UUIDv4` перед каждой отправкой запроса:
```javascript
// Автоматическая генерация UUIDv4 для заголовка идемпотентности
pm.request.headers.add({
    key: 'X-Idempotency-Key',
    value: pm.variables.replaceIn('{{$guid}}')
});
```

### 3. Tests (автоматические проверки ответа)
После выполнения запроса Postman проверяет статус, SLA времени ответа и структуру JSON:
```javascript
pm.test("Status code is 201 Created", function () {
    pm.response.to.have.status(201);
});

pm.test("Response has documentId and status is PROCESSING", function () {
    var jsonData = pm.response.json();
    pm.expect(jsonData).to.have.property('documentId');
    pm.expect(jsonData.status).to.eql("PROCESSING");
    
    pm.environment.set("lastCreatedDocId", jsonData.documentId);
});
```

## 🎯 Практическая ценность для L2-поддержки
* **Снижение нагрузки на поддержку:** внешние команды получают готовый сценарий запуска, правила ретраев и разбор заголовков.
* **Быстрое воспроизведение инцидентов:** L2-инженер может в 1 клик воспроизвести кейс клиента в Postman и отличить ошибку входных данных (`400`/`422`) от сбоя на стороне сервиса (`504`).
